## プロジェクト背景

AmeCompression（雨 Compression）は、FFmpeg を使用したビデオ (SVT-AV1) およびオーディオ (MP3) 圧縮アプリケーションです。
技術スタック: Electron + React + TypeScript (フロントエンド) / Python + Flask (バックエンド)。
このプロジェクトは「世界最高のビデオおよびオーディオ圧縮アプリケーション」を目指しており、すべてのコード・UI・エラーメッセージ・応答時間がこの目標に寄与する必要があります。

## レビュー観点（静的解析ツールがカバーしない高コンテキスト領域のみ）

### 1. プロジェクト固有のアーキテクチャ・設計（一貫性）

* **レビュー項目:**
* バックエンド: `backend/video.py` (SVT-AV1 CRF/preset)、`backend/audio.py` (libmp3lame)、`backend/ffmpeg.py`、`backend/volume.py`、`backend/job_runner.py`、`backend/api/` (Flask REST API) の既存ユーティリティが適切に使われているか。
* フロントエンド: `frontend/src/services/api.ts` の共有 Axios インスタンスが使われているか。型定義は `frontend/src/types/index.ts` から import されているか。状態管理は useState / useRef / Context の既存パターンに従っているか。
* 新しく共通ユーティリティを作る前に既存のものが流用できないか。重複実装になっていないか。

### 2. コーディング規約の遵守（AGENTS.md 準拠）

* **レビュー項目:**
* エラー抑制コメント（`# type: ignore`, `# noqa`, `eslint-disable`, `@ts-ignore`, `@ts-nocheck`）が追加されていないか。禁止事項（AGENTS.md §4.1）違反は必ず指摘すること。
* 本番コードでの `console.log`、バックエンド API コードでの `print()` が残っていないか（AGENTS.md §4.2）。
* ユーザー向け文字列がハードコードされず、`frontend/src/i18n/en.json` / `ja.json` の両方にキーが追加されているか（ドット記法）。
* ノイズ除去レベル (0.0〜1.0) を FFmpeg の `nr` に渡す際、`max(0.01, denoise_level * 97)` の変換が適用されているか。UI の生値をそのまま `nr` に渡していないか。
* FFmpeg 子プロセスは必ず `finally` で終了し、ゾンビプロセスを残さない実装になっているか。
* 型安全性: `Optional` / `None` は必ずガードされているか。`any` 型が使われていないか。

### 3. コンテキストの整合性（論理的妥当性）

* **レビュー項目:**

* クロスファイルの契約（関数シグネチャ・戻り値スキーマ・import の存在・API レスポンス形式）が維持されているか。

### 4. ドキュメントと変更背景の明文化（保守性）

* **レビュー項目:**
* コードの変更に伴い、関連する README やコメント（Why - なぜその実装にしたか）が更新されているか。

* 新しい設定値や API エンドポイントを追加した場合、対応するドキュメントが更新されているか。

## 静的解析ツールが担当する項目（AIは指摘しないこと）

以下は Ruff / Mypy / Pyright / ESLint / tsc / Shellcheck / actionlint / gitleaks / yamllint / codespell が検出するため、AIはこれらを重複して指摘しないでください:

* 型注記の正確性、未使用 import、docstring の有無（ruff D100-D107 準拠）
* broad exception catch (BLE001)、assert の本番使用 (S101)
* フォーマット・スタイル・命名の機械的規約（PEP 8 / Prettier / ESLint）
* 古典的インジェクション脆弱性、シークレットハードコード、パストラバーサル（gitleaks / semgrep）
* シェルの引用符欠落、mktemp/trap 対、echo|python3 -c パターン、kill -15 $pids

## 禁止事項（ガードレール・厳守）

* `# noqa` / `# type: ignore` / `eslint-disable` 等のエラー抑制コメントを修正案として提案してはならない。根本原因を修正する案を提示すること。
* 静的解析ツールが検出する項目（上記）を重複して指摘してはならない。
* docstring の有無・内容を指摘してはならない（ruff 設定に準拠）。

## 収束指示

* 既存指摘への対応が完了しており、新たに CRITICAL/HIGH/MIDDLE に該当しない場合は comments を空配列にすること。
* 微細な改善提案は LOW とし、必須修正として扱わないこと。
* テストのみの差分（本番コードの変更を含まない）の場合、テストが文書化する挙動は実装の検証済み仕様とみなすこと。実装ファイルが差分に含まれなくても「実装が対応しているか確認してください」と繰り返し指摘してはならない。テストの内容が意味的に正しく、既存のテストスタイルに沿っていれば、その旨の指摘はしないこと。
